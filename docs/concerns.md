# Concerns

Things we noticed that don't block the current work. Blockers get fixed in the slice
that finds them. These get solved later, or written up in NOTES.md §5 if we don't.

| # | Concern | Where it bites | Solve in / when |
| --- | --- | --- | --- |
| K1 | `error` carries three things: why a step is unresolved, why it failed, and a warning on a completed step (D2). A tool that only reads `status` misses a corruption warning | Scientists and tools reading REST | GraphQL: a separate data-integrity field |
| K2 | A step holds one attempt. Evidence for an earlier job is dropped, not kept as history | Retries: the record can't show what earlier attempts did | Done: every attempt kept (lifecycle slice), and facts for an earlier job reach it (store slice, K45) |
| K3 | A failed outcome with an empty instrument error gives `error: null` | Failed steps without an explanation | When the driver's failure events are built (S4): always send a message |
| K4 | A wrong `DataLost` while an upload is only slow fails the read until a matching `DataStored` arrives | Brief false failure under storage outages | Done in R1: `data_lost` only from a restarted driver, after storage says absent past the upload grace |
| K5 | A re-read after data loss is a second ledger execution, so acceptance check 5 fails under chaos | Chaos runs look like duplicate runs | NOTES.md: explain it as honest |
| K6 | Operator "declare lost" for a driver that never comes back is deferred (D1) | Runs stuck forever as running | GraphQL mutation, if time allows |
| K7 | `tmp/smoke`, `tmp/exp-*` are Go packages under `./...`, so `go vet ./...` checks them (only `_`-prefixed dirs are skipped) | Local vet/test noise | Rename to `_`-prefixed or delete; not ours to touch |
| K8 | The C1 probe lives only in `tmp/_natsprobe` (local), so the experiment can't be rerun from the repo | Reproducing C1 | Commit it if reviewers ask |
| K9 | Which steps produce data is decided by device name (`plate-reader*`, `store.go` `producesData`) | A new data-producing device would complete without its data being checked | When drivers announce themselves: let them advertise `produces_data` |
| K10 | `steps.lifecycle` is the Go `Step` as JSON with no version. Renaming a field silently drops it from rows already stored | Any later change to `Step` | Done (lifecycle slice): `V` in the JSON; any other version is refused with a reset hint |
| K11 | The store's guarantee depends on its callers: an event consumer must ack only after `applyToJob` returns nil, and a claim reply must reflect the returned Step | S5: acking early loses facts; replying from a stale read breaks claim/cancel | S5, as part of its check |
| K12 | Each apply locks one row, so there are no deadlocks today. A later transaction that locks several steps, such as a run-wide cancel, must lock them in a fixed order | Run-level operations in S5 / cancel | Lock in `position` order |
| K13 | Device ids go into subjects unchecked: a `.`, `*` or `>` in a device name from `workflows.yaml` breaks or widens subjects | A typo in workflows.yaml | Validate device names when workflows load |
| K14 | No rolling-upgrade story: a v2 driver against a v1 executor has every message rejected (fails safe, not zero-downtime) | Deploys | Out of scope; NOTES.md |
| K15 | An event's `device` should equal the device in its subject | A mis-wired driver reporting for another device | Done in S5a, and the step's assigned device must match too (Codex) |
| K16 | (Codex, S4) If the instrument's end-of-job ledger write fails, `Status()` says completed and we publish it, but after a restart the ledger file says hung (`instrument.go:241`). The record would then disagree with the ledger | Needs a disk error; no chaos tool causes it | Accepted; NOTES.md §5. We cannot see a failed ledger write from outside the instrument |
| K17 | (Codex, S4) The driver drops the plate reader's `Outcome.Data`: a read finishes but is never stored, so it stays `storing` | Any plate read until S6 | Done in S6 (upload, then `stored`); `data_lost` moves to R1 (K32) |
| K18 | (Codex, S4) A driver restart between the ledger outcome and the acked `finished` publish loses that event; a repeated command then gets `known` and nothing reports it | Driver crash mid-report | Done in R1: ledger outcomes replayed on start |
| K19 | A claim granted but `Run` returns `ErrBusy` (instrument busy with a job we did not start): the step stays claimed and nothing ran | Rare: an instrument busy outside our knowledge | Done (S7): the same job is resent while claimed with no evidence; the driver accepts it again once the instrument is free, since nothing ran |
| K20 | The driver calls `inst.Status()` (a copy of the whole ledger) on every command and every 50ms while a job runs | Long-lived ledgers with many thousands of entries | Fine at this scale; look up by job id if it shows |
| K21 | `stored` events are Nak'd every 30s until S6 handles them | None today: no driver publishes `stored` yet | Done in S6 |
| K22 | `LAB_EVENTS` keeps everything (no `MaxAge`/limits) | Disk on a long-lived NATS | Set retention once replay needs (R1) are known |
| K23 | A Term'd (malformed) event is only logged; there is no dead-letter place to inspect it later | Debugging a misbehaving driver | Advisory or a DLQ stream if it shows up |
| K24 | Claims are handled one at a time per executor (one subscription); a slow database delays every claim, and drivers keep asking | DB latency spikes | Fine at three devices; worker pool if needed |
| K25 | A step claimed but never started (driver died after the claim), or hung, keeps its run `running` forever | Driver crashes, instrument hangs | Done: hangs by D4; claimed-never-started by S7's resend (live repro in the S7 PR) |
| K26 | (Done in R1, D3) A late `DataStored` after `DataLost` turned a failed read into completed, after its run was already finished as failed | Storage slow enough that the driver gave up on it | Re-evaluate a finished run when a step changes, or freeze evidence once a run ends |
| K27 | Steps after a failed one stay `pending` in a failed run (never sent, so true, but a reader may expect `cancelled`) | API/GraphQL readers | GraphQL: say why a step never ran |
| K28 | Every 500ms the loop rescans all running runs, one query per run | Many concurrent runs | Fine at this scale; one joined query or LISTEN/NOTIFY if it shows |
| K29 | Runs that share a device only retry on `busy`; no fairness or queueing across runs | Several runs at once on one instrument | Out of scope unless chaos shows starvation |
| K30 | While storage is down the plate reader is held (busy) until its bytes are stored; a long outage stops all reads | Storage outages | Intended: one copy in memory, never dropped. Chaos-test it; a spool to disk if it bites |
| K31 | A `stored` event whose object is missing or unreadable is checked again every 2s, for ever (e.g. the object was deleted) | Storage loses an object | The step stays `running`, which is true; S7/operator can resolve |
| K32 | A driver restart between a read and its upload loses the bytes; the read stays `running` for ever. Seen on the stack: `run-8c366ff2ecb6` (S5b run, driver rebuilt) | Driver crashes, every redeploy mid-read | Done in R1 (with the Codex cases: upload still landing, storage down) |
| K33 | Each redelivery of a `stored` event adds another storage check to the step (`Checks` grows) | Only when an ack is lost after the commit | Fine; dedupe checks by SHA if it grows |
| K34 | (Codex, S6) A verified read whose object later disappears still says `completed` with a `data_ref` to nothing. A redelivered `stored` (lost ack) that then fails to read back only retries | Objects deleted after verification | D2-style warning from a periodic re-check of completed reads' objects; not on the event path |
| K35 | Replay publishes every ended job in the ledger on every start; the ledger only grows | Long-lived instruments, frequent restarts | Fine at this scale; replay only jobs newer than a checkpoint if it shows |
| K36 | The upload grace (2 x 5s storage timeout) only delays a `data_lost` report; correctness no longer depends on it (D3) | A storage server that commits a dead client's upload very late | `/break`: kill the plate reader mid-upload; would need a storage-side test to measure |
| K37 | Each restart re-sends `stored` for every stored read, and the executor reads each object back again | Restarts with many past reads | Same as K35 |
| K38 | That replay uses only the ledger as it was before listening (so a new read mid-upload is never called lost) is shown by the code, not by a test: `TestReplayLeavesNewJobsAlone` passes either way, since replay finishes before a command arrives | A change that reads the live ledger in replay | Keep the snapshot; a test would need a slow replay |
| K39 | A read reported lost keeps its run `running` until the object appears or someone decides; nothing decides yet | Every real data loss | Narrowed by D4: a re-read ends it unless the re-reads also fail. For the rest, operator `abandonStep` (D4, deferred) |
| K40 | The recheck reads every lost read's object every 10s, for ever | Many lost reads | Back off per read if it shows |
| K41 | Runs already finished as failed by the old rule (e.g. `run-8c366ff2ecb6` on the local stack) are not reopened | Local data from before D3 | Discard local data, or a one-off migration if it mattered |
| K42 | `finish` has no rule for a run with a cancelled step (it never finishes), and D4 decides only steps: whether the run ends `cancelled`, or `failed` when a claimed attempt failed after the cancel, is open | `CancelRun` | Done (cancel slice, D5): rule 1. `completed` if every step completed, `failed` if the policy gave up on a step for its own reason, else `cancelled` |
| K43 | A driver stopped between the ledger's end of a failed job and `Run`'s return publishes no `finished`; replay reports it without `retryable`, so the step fails instead of retrying | Driver restarts at that instant (a window of microseconds) | Accepted: errs on not repeating (D4) |
| K44 | Reading `Run`'s result before it returns is caught only by `go test -race` (mutation check, D4 protocol slice); the plain suite passes, because the 50ms ledger poll almost always lets `Run` return first | A change to the driver's finish path | Done: the slice verify step and CLAUDE.md run `go test -race ./...` |
| K45 | Driver events find their step by the `job_id` column, which holds only the latest attempt's job; an event for an earlier attempt is acked as unknown and dropped | Any second attempt (none yet: nothing retries) | Done (store slice): found by run and step parsed from the job id, from the assigned device, and only for a job the step has an attempt for |
| K46 | A step can move from `failed` back to `unresolved` when a conflicting outcome arrives for an ended attempt; its run, already finished `failed`, is not reopened | A duplicate or corrupted ledger report after a give-up | As before D4 (a conflict always showed); say so in the error if it shows |
| K47 | `command` sends `attempt: 1` whatever the step's attempt (`send.go`, `NewRunCommand(runID, s.name, 1)`) | The first retry | Done (policy slice): the command's attempt comes from the job id |
| K48 | Until the policy slice, a plate-reader hang ends `failed` ("not repeated") although D4 makes it repeat-safe | `PR_HANG_PCT` > 0 | Done (policy slice): `REPEAT_SAFE` defaults to the plate reader |
| K49 | The lost-read recheck now decodes every unresolved step to find lost attempts, not only lost ones | Many unresolved steps | Widened by the policy slice: every running step is decoded every 10s, so a lost read is found while its re-read is in flight. Filter in SQL with a jsonpath if it shows |
| K50 | The dispatch loop takes a row lock every 500ms for each `ended` or `unresolved` step, even when the policy has nothing to do (a lost read at the limit, a mismatch, a conflict) | Many unresolved steps | Skip steps whose decision cannot change until a new fact arrives |
| K51 | A retry is sent at once, with no backoff: a device that fails every time uses its 3 attempts within seconds | Transient faults that last longer than a few seconds | Backoff per attempt, if a `/break` run shows it matters |
| K52 | With retries, acceptance check 5 ("no step ran more than once") fails on any run that retried; each attempt is its own job in the ledger (K5) | `/break` runs with faults | Read check 5 per job, or note it in NOTES.md |
| K53 | With retries, the REST step (`started_at`, `finished_at`) and `/timeline` show only the attempt that decided the step: an earlier attempt that occupied the device (C3b: a 30s hang on the plate reader) does not appear | Reading device occupancy from the API after a retry | GraphQL attempts history; consider listing each attempt in `/timeline` (its shape is fixed, so maybe GraphQL only) |
| K54 | A cancel that arrives after an attempt's claim, when the job never started (the driver died), does not stop it: S7's resend runs it once the driver is back. D1: a claimed attempt is not stopped | `CancelRun` | Done (cancel slice, D5): a re-claim after a cancel, with no evidence, withdraws the claim and answers `abort`; measured live, nothing in the ledger |
| K55 | "A resend never runs a job twice" rests on the instrument's ledger surviving restarts and on one driver process per instrument. A wiped ledger directory, or a second driver for the same instrument, would let a resend run again | Ops mistakes; not reachable in this stack | State it in NOTES.md as an assumption |
| K56 | (Codex, cancel slice) A withdrawn claim assumes a second claim for a job means the first was never acted on. With two executors in the queue group, a driver's first claim can stall in one executor while its retry is granted by the other and the job runs; if a cancel then commits before the stalled claim, that claim is read as a re-claim and withdraws an attempt that is running. The record would say `cancelled` until the job's events arrive, and the run could finish first | Several executor replicas; not reachable with one executor | Deferred (user). State "one executor" in NOTES.md beside K55; with replicas, have the driver number its claims so a stale one is recognised |
| K57 | A mutant that judges the latest attempt instead of the one that ran, after a cancel, survives: a withdrawn attempt is always a retry the policy allowed, so both give `not retried: cancelled`. It would differ only if `MAX_ATTEMPTS` or `REPEAT_SAFE` changed across a restart | Config change mid-run | Accepted; noted so a reviewer doesn't take it for a gap |
