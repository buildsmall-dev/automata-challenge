Executor–driver messaging

How an executor and instrument drivers communicate over NATS.

Status: awaiting choice

1. The question

How do commands reach the drivers, and how do outcomes get back to the executor, so the run record stays true when messages are lost, duplicated or late, and when processes or networks drop?

  • The executor owns runs and keeps them in Postgres. It talks to 3 drivers (liquid handler, incubator, plate reader) over NATS.
  • Each instrument does one job at a time and keeps a durable ledger of every physical execution, written before work starts and surviving restarts.
  • The plate reader produces data that must be stored in S3.

2. Correctness comes from four things, not the transport

1Durable intent first

The executor writes job_id + attempt to Postgres before sending, so after a crash it knows what it may have sent.

2Predictable JobID

E.g. run-abc/combine/1. On any command the driver checks the instrument ledger: already running or done? Report it, don't run again. A duplicate message never becomes a second physical run.

3Guarded state changes

E.g. UPDATE steps … WHERE job_id=$1 AND status='running'. Late or duplicate results can't move a step backwards or overwrite a newer attempt.

4Re-discoverable truth

The executor can always ask the driver (answers from the ledger) or check storage. Data key derived from job id (runs/<run>/<step>/<job_id>.csv); compare its sha256 with the ledger's.

The transport decides how much buffering and retrying we write ourselves — not whether we're correct.

3. Life of a job

The diagram shows the happy path. The options below differ in how the two arrows crossing NATS are carried and what the executor does when one is lost.

4. Three options

A. Core request/reply; executor asks for the truth

How it works

  • lab.<device>.run {job_id, run_id, step}: driver replies accepted | busy | known and runs in the background.
  • lab.<device>.job {job_id}: driver answers from ledger + upload state: running | completed(times, ref) | failed(retryable) | hung.
  • Executor loop every ~500ms: ask about every in-flight job, apply with a guarded update; call NextSteps and dispatch.
  • Optional lossy core "job changed" nudge so the executor asks immediately. Losing it is harmless.

Makes easy

  • Recovery is the normal path (exercised every run).
  • No stream state.
  • Cancel = stop dispatching (nothing queued).
  • Busy device: step stays pending (nothing ran).

Makes hard

  • Up to one tick of latency (times come from the ledger, so no accuracy loss).
  • Executor does cross-run device queueing.
  • Wouldn't scale to thousands of devices (not a concern here).
Rests on: "anything the executor needs it can find out again by asking." Verdict: true for physical outcomes (durable ledger) and for data (predictable key + sha). Not true for plate data bytes never uploaded if the driver restarts first. That is equally true for B and C. The honest record is a failed attempt "data lost", retried (reads are retryable).

B. JetStream both ways

How it works

  • Stream CMDS (cmd.<device>, work-queue, durable pull consumer per device, MaxAckPending=1); stream EVENTS (evt.<device>, durable consumer on the executor).
  • Commands published with Nats-Msg-Id=job_id.
  • Driver: fetch, ledger check, run, publish started/finished (retry until PubAck), then ack the command (InProgress heartbeats meanwhile).
  • Executor applies events in a DB transaction, acks after commit.

Makes easy

  • Messages wait across executor outages and driver disconnects.
  • Natural per-device queue across runs.
  • Event history.

Makes hard

  • AckWait vs step duration and 30s hangs (lost heartbeat means redelivery while still running).
  • 2-minute dedupe window.
  • Queued commands for runs cancelled since.
  • A second place state lives (stream vs Postgres).
Rests on: "durable messaging keeps the record true." Verdict: only partly. It adds buffering, not correctness.
  • At-least-once means duplicates (still need the ledger check).
  • A crash between DB write and publish loses the command (still need reconcile).
  • Hangs send no event (still need a deadline).

C. Hybrid: request/reply commands + JetStream events + status query

How it works

  • Commands as in A (synchronous, no stale queue).
  • Results go to the EVENTS stream (Msg-Id, retried until acked), consumed durably.
  • A's lab.<device>.job query for startup recovery and silent steps.

Makes easy

  • Buffering in the direction that matters most (driver facts while the executor is down).

Makes hard

  • Two mechanisms, two recovery paths.
  • Still needs A's query.
Rests on: "push events are needed for correctness or latency." Verdict: not for correctness. For latency, a core nudge gets most of the way.

6. What we know

Inferred from code:
  • The ledger records the JobID before work and survives restarts.
  • Status() shows the current job and every execution.
  • Plate reader bytes exist only in memory in the Outcome.
  • Both processes reconnect to NATS forever.
Guess worth measuring: what chaos.sh disconnect (docker network disconnect) does to an open NATS connection.
  • The TCP connection may survive a 2–7s gap, or the client may notice only via pings (nats.go default 2 min × 2), silently losing core publishes in the window.
  • Matters a lot for B/C; A's correctness doesn't depend on it.
  • Proposed ~10 min experiment: publish numbered core messages every 200ms plus a request every second while disconnecting the container. Record what arrives, how long requests take to fail, and when the client notices.

Measured nothing yet.

7. Recommendation

Recommendation, not the decision · status: awaiting choice

A + lossy core nudge

Why:

  • Every guarantee rests on things durable on their own (Postgres, ledger, storage), not on messages getting through.
  • The recovery path is the normal path.
  • Smallest system to explain.

Honest cost: no JetStream, although the README switches it on. Defensible because JetStream buys buffering, and this design doesn't need buffering to be correct.

Would change my mind if:

  • The disconnect experiment shows requests hanging for minutes (fixable with ping settings).
  • Queueing several runs per device is wanted (B gives it free).
  • Stream event history is wanted as part of the record.
