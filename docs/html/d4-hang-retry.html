1. The problem: three ways a step gets stuck

Every step the executor sends can end in one of a few ways. Most are already handled: completed (with verified data, for a read) and failed (the instrument reported an error). Three cases are not handled. Today each leaves its step, and so its whole run, stuck:

Hung

The instrument hangs, frees itself after 30s, and writes hung in its ledger. Our driver reports finished(hung). The step becomes unresolved (API: running) and stays that way forever.

Data lost

The plate reader completed the read, but the bytes died with a driver restart. Under D3 the read stays unresolved in case a late upload lands. Nothing ever ends it.

Failed

The instrument reported an error. The step is failed and the run fails, even when the instrument itself said "this can be retried".

A fourth case, claimed but never started (the driver died between the claim and pressing start), is not part of this decision. Nothing physical happened, so the fix is to resend the same job, not start a new attempt. That is reconcile (S7).

Why this matters for truth. A step that says running forever after the instrument stopped is a claim that is no longer true. A careless retry can be physically wrong: if a hung liquid handler did dispense, a retry dispenses twice. So the policy has to be both live (runs end) and safe (nothing is repeated that should not be).

2. Words we need

Attempt
One try at one step. Attempt 1 is the first. A retry is attempt 2, and so on.
Job id
run/step/attempt, e.g. run-8c36/read_plate/2. The instrument records it in its ledger. A repeated command for the same job is recognised and never runs twice (the driver answers known). A new attempt has a new job id, so it does run again. That is the whole point of a retry, and also its danger.
Ledger
The instrument's own diary: one entry per physical execution, with completed / failed / hung and times. Our best evidence.
Repeat-safe
A property of a device's operation: doing it again after an unknown outcome does no harm. Reading a plate is (it only looks). Dispensing liquid is not (you cannot un-dispense). Incubating is probably safe for a short extra time, but that is a guess about real chemistry.

4. The measurement: faults are the same in every run

The instrument decides whether a job fails or hangs by hashing four things:

roll = sha256(seed : device : step : attempt) % 100

The run id is not in it. And attempt is how many times this run already executed this step on the instrument. So, under one seed, the first try of a given step has the same fate in every run. Only a later attempt rolls a new number.

We copied the instrument's roll function and computed it for the real workflow steps, seed 0. A cell is HANG when the roll is below 30, which is what *_HANG_PCT=30 does. measured

5. The three options

A. No automatic retry: an operator decides

Hung and lost steps stay unresolved (API running). Failed stays failed. We add GraphQL mutations retryStep (start a new attempt) and abandonStep (mark it failed with "abandoned by operator").

Easy: never repeats anything physical by itself; smallest code.
Hard: under any fault seed, runs never end on their own (see the table). Needs a person watching.
Rests on: "repeating a lab operation is unsafe in general". True for liquid handling, false for a plate read.

B. Automatic, bounded, per device recommended

Each device declares repeat_safe in config. Proposed: plate reader yes, incubator yes, liquid handler no. Then the executor starts a new attempt when:

  • failed and the instrument said Retryable;
  • hung on a repeat-safe device, only after finished(hung) arrives. The instrument is free by then, so there is no timer and no clock to trust;
  • data lost on the plate reader: re-read the plate.

At most 3 attempts in total. When attempts run out, or the device is not repeat-safe, the step is failed with the full reason. Every attempt stays in the record.

Easy: runs end on their own; safe devices recover; the record shows every try.
Hard: attempt history in the lifecycle (a schema change); events for old attempts must still find their step; check 5 fails under faults.
Rests on: repeat-safety can be stated honestly per device. True of this simulator's config, a guess about real equipment.

C. Retry only on the instrument's own Retryable flag

No device config. Retry a failure when Retryable is true.

The gap: a hang returns no Outcome, so there is no flag. C must either never retry hangs (then it is A for hangs) or always retry them (then it double- dispenses on the liquid handler). It does not answer the question for the hardest case.

7. Walk-through: a hung incubation under option B

  1. The executor sends run-x/incubate_samples/1. The driver claims it and starts the instrument.
  2. The instrument hangs. The ledger says running. The record says running, which is true.
  3. After 30s the instrument frees itself and writes hung. The driver publishes finished(hung).
  4. The executor applies it. Attempt 1 is now final: "hung, outcome unknown". The incubator is repeat-safe and this was attempt 1 of 3, so a Retry fact opens attempt 2.
  5. The dispatch loop sends run-x/incubate_samples/2, a new job id, so the driver accepts it. Claim, run, report, as usual.
  6. Attempt 2 completes. The step is completed, and the run moves on.

The same steps on the liquid handler stop at step 4. It is not repeat-safe, so the step becomes failed with "instrument hung; outcome unknown; not repeated: liquid handling is not safe to repeat", and the run ends failed.

There is no timer anywhere. The retry is triggered by the instrument's own report that it gave up. That also avoids sending attempt 2 while the instrument is still frozen, which today would get busy or, worse, a granted claim and ErrBusy (K19).

8. What the record looks like with attempts

Today a step holds one attempt (concern K2). Under B a step holds a list. The step's status comes from its latest attempt. Older attempts are kept as history and still accept late facts.

incubate_samples                   status: completed   (from attempt 2)
  attempt 1  run-x/incubate_samples/1   hung       09:00:02 – 09:00:32   outcome unknown
  attempt 2  run-x/incubate_samples/2   completed  09:00:33 – 09:00:35
  • REST (fixed shape): shows the latest attempt only: its status, times and error. The API can't change, so history isn't visible there.
  • GraphQL: exposes attempts, so a scientist can see that the incubator hung once before it worked.
  • Finding a step from an old job id: today we look up steps.job_id, which only holds the current attempt. A late event for attempt 1 would be dropped as "unknown job". Instead we parse the job id (run/step/attempt) to find the step, then the attempt inside it.
  • Ledger vs record: the ledger has two executions; the record has two attempts. They agree. Acceptance check 5 still says "ran more than once", because it counts executions per step name. That is the honest result under faults (K5), and NOTES.md explains it.

9. The open question: what status does a final hang get?

When a hung attempt will not be repeated (unsafe device, or attempts used up), the step needs a status. The API only has pending / running / completed / failed / cancelled.

failed, with "outcome unknown" (recommended)

CLAUDE.md: "running while we can still find out, and failed with the reason once we can't." After the ledger says hung we can't find out any more. failed means "this step did not achieve its result". It does not claim the instrument did nothing. The error says the physical outcome is unknown.

The run can end, as failed.

running until an operator acts

Keeps your S1 point, "a hung job doesn't necessarily mean failed", literally. But running claims something is still happening, and the instrument has stopped and moved on. Arguably that is the less true of the two.

The run stays open until someone decides.

How this differs from data lost (D3). After a hang, the ledger's word is final: no later evidence can come. After a data loss, a late upload can still land. So a final hang may be failed, but a lost read with no retry left stays unresolved. Under B that only happens if all 3 re-reads lose their data.

11. What you are deciding

  1. Policy: A (operator), B (automatic, per device), or C (instrument's flag).
  2. Final hang status: failed + "outcome unknown", or running until an operator acts.
  3. If B: which devices are repeat-safe (proposed: plate reader, incubator) and how many attempts (proposed: 3).

What would change the recommendation: if repeat-safety can't be stated honestly per device, choose A. If acceptance check 5 must hold even with faults on, choose A.
