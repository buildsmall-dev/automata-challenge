Executor–driver messaging v2

Production lens. Option C chosen by the user; amendments from a measured experiment.

Chosen: C (hybrid), with amendments. Recorded as D1 in docs/decisions.md

1. What changed since v1

  • v1 weighted simplicity and recommended A (polling).
  • Re-judged on production reliability, scalability, maintainability and operational complexity. The facts didn't change; their weight did.
  • A's key assumption, "we can always ask the instrument", is true of this simulator's complete ledger but false of most real equipment.

2. Production requirements

Fail-safe actuation

When in doubt, don't move. A late command is worse than none.

Facts survive executor downtime

Not only in driver memory.

Don't depend on instrument history

The ledger is a cross-check, not the only record.

Operability

Lag, redeliveries and stuck jobs are visible as metrics.

v1's four correctness rules still hold:

1 Durable intent first
2 Predictable JobID checked against ledger
3 Guarded state changes
4 Re-discoverable truth

4. Option C topology

  • Commands: core request lab.<device>.cmd.run {v, job_id, run_id, step, attempt}, reply accepted | busy | known. The executor keeps the queue in Postgres and sends only to a device it believes free.
  • Claim before run: before inst.Run the driver requests lab.executor.claim {job_id}; only go starts physical work (§7.1).
  • Events: the driver publishes accepted / started / finished to JetStream stream LAB_EVENTS (subjects lab.<device>.evt.*) with Nats-Msg-Id = job_id + kind, retried until PubAck. The executor uses a durable pull consumer, applies events idempotently, and acks after the DB commit.
  • Reconcile query: lab.<device>.job request/reply, answered from ledger + storage. Used on executor startup and for in-flight steps past their deadline.
  • The executor provisions the stream (CreateOrUpdateStream) at startup; drivers never create infra.

F1. A timeout does not mean not delivered.

Timed-out requests were delivered up to ~20s late, after the sender gave up. A "run job" command can reach a driver after the executor timed out, even after a cancel.

→ The driver claims every job with the executor before running it (§7.1), so a late command after a cancel is refused. Expiry would only narrow the window, so it isn't needed. The executor treats a timeout as "unknown", resends the same job_id (never a new attempt), and doesn't consider the device free.

F2. A failed JetStream publish may have been stored.

7 of 8 publishes that returned "context deadline exceeded" were in the stream.

→ The driver retries with the same Nats-Msg-Id (the server dedupes within its 2-minute window). The executor applies events idempotently, because partitions longer than the window can still produce duplicates.

F3. Ping interval trades lateness for loss.

Default pings (the drivers' current setting, 2 min) made a 20s partition invisible: nothing lost, everything late. 2s pings detected it in ~6s but lost what was written into the dead socket; later publishes were buffered and flushed on reconnect.

→ Both are handled by F1 + F2, so correctness doesn't depend on the setting. Set it explicitly (a few seconds) for faster detection and visible disconnect events.

6. Driver crashes after the operation, before the event Inferred

From instrument.go: the ledger is updated to completed before Run returns the Outcome, and a restart leaves completed entries untouched.

W1. Plate reader, before the S3 upload
ledger completed→crash→S3 upload→event

Data bytes exist only in driver memory, so they are lost for good. Ledger has completed + sha256, storage has nothing. True record: that attempt failed, "data lost before storage". Retry the read (reads are retryable); the ledger will honestly show two executions.

W2. After upload, before JetStream ack
ledger completed→S3 upload→crash→event

Recoverable. The object exists at the deterministic key; no event. Data present, hash matches ledger.

W3. Non-data step completed, before the event
ledger completed→crash→event

Recoverable from the ledger (completed, no event).

Recovery paths (belt and braces)

  • R1. Driver startup replay: on start, read the ledger and publish finished events for recent executions, checking storage for the plate object. Msg-Id dedupe + idempotent apply make repeats harmless.
  • R2. Executor deadline + reconcile query: covers a driver that stays down or restarts silently.
Both paths rely on the instrument's own durable record. Without it (some real devices), this window cannot be closed in software: the honest record is "outcome unknown", and for the liquid handler that needs a human.
Also a simulator artifact: a driver crash during a job here kills the simulated work and the ledger marks it hung, "instrument restarted during the job". A real instrument would carry on.

7. Clarified cases Inferred

7.1 No command runs after a cancel: claim before run

Expiry only narrows the late-command window. Instead, the driver asks lab.executor.claim {job_id} before inst.Run, and the executor does one conditional update:

UPDATE steps SET phase = 'claimed'
 WHERE job_id = $1 AND phase = 'dispatched'
   AND run is not cancelled   -- serialises with CancelRun on the same row
Claim replyDriver does
go (1 row)Runs the job. A later cancel can't stop it, so the record shows its real outcome.
abort (0 rows)Nothing physical. Cancelled, superseded or unknown job.
timeoutDon't run. Retry the claim with the same job_id; claims are idempotent.
  • Why it holds: cancel and claim change the same row, so Postgres orders them and exactly one wins. A cancel stops what hasn't started.
  • Lost "go": the DB says claimed but nothing ran. The deadline expires, the reconcile query finds no ledger entry for the job_id, and the step returns to dispatched with the same job_id.
  • Executor down: no new physical work starts (fail-safe).

7.2 Driver stays offline and reconciliation isn't possible

Contact lostWhat we knowRecord says
Before the claim was grantedNothing ran (our own DB proves it)Step pending; the run waits, other branches continue; a cancel makes it cancelled
After the claim was grantedIt may be running, done, failed or hungStep running, error "driver unreachable since T, outcome unknown"
  • Unknown stays unknown. Never mark it failed on a timer: if it completed, the record would contradict the ledger. Internal phase unknown + last contact time; GraphQL can expose outcomeKnown.
  • Late facts always win. When the driver returns, R1/R2 apply the real outcome, even hours later and even if the run was cancelled meanwhile. A cancel never overwrites a running step.
  • A driver that never returns: the step stays unknown. An operator "declare lost" action (recorded as a human statement) is deferred.

7.3 A completed read vs missing data

Two independent sources: the ledger (read happened, sha256) and storage (object at runs/<run>/<step>/<job_id>.csv). The executor fetches the object and hashes it itself before it sets data_ref.

7.4 Internal phases

dispatched → API pending
claimed · running · storing · unknown → API running
completed · failed · cancelled → same

The scheduler counts a dispatched step as occupying its device.

8. Remaining limitations

  • acceptedCrash window W1 loses plate data; costs a re-read.
  • acceptedOutcome after a driver crash is only as durable as the instrument's history (stated in the note).
  • acceptedClaim before run needs the executor reachable before every physical start: one extra round trip, and no new work while it is down (fail-safe).
  • acceptedA driver that never comes back leaves a claimed step "running, outcome unknown" for good. An operator "declare lost" action is deferred.
  • acceptedA re-read after data loss is a second ledger execution: honest, but it fails acceptance check 5 under chaos.
  • acceptedJetStream dedupe window is 2 minutes; longer partitions rely on idempotent apply.
  • acceptedDriver holds an event in memory until PubAck; a crash is recovered by R1/R2.
  • out of scopeSingle NATS server, single-replica stream: NATS down = no progress (fail-safe, not HA).
  • out of scopeSingle executor; replicas would need per-run locking.
  • acceptedMeasured on Docker Desktop for Mac with docker network disconnect; real networks may behave differently.
